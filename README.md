# chess_z

一个用 C 语言实现的中国象棋软件框架。当前重点是规则核心和 AI 接入边界：

- 90 格棋盘使用双 `uint64_t` 位棋盘表示，每方每类棋子都有独立 bitboard。
- 同步维护 `board[90]` 邮箱数组，便于规则生成和调试。
- 支持初始局面、FEN 读写、走子、合法着法生成、将军检测和 perft。
- 提供 `XqEngineAdapter`，可为内置搜索接入自定义估值和走法排序函数。
- 内置子力与位置估值、迭代加深 negamax 搜索，以及可选的固定视角并行 Minimax。

## 构建

推荐使用 CMake（需要支持 C11 的编译器）：

```sh
cmake -S . -B build
cmake --build build
```

编译交互式人机示例：

```sh
gcc -pthread -std=c11 -O2 -Wall -Wextra -Wpedantic -I include src/position.c src/movegen.c src/history.c src/engine.c src/parallel_search.c src/search_sampling.c examples/cli.c examples/search_progress.c examples/search_sample_report.c -o build/xiangqi_cli
./build/xiangqi_cli
```

## 实时搜索进度

两种搜索模式均可加 `--progress`，默认关闭：

```sh
./build/xiangqi_cli --engine red --depth 10 --time-ms 5000 --progress
./build/xiangqi_cli --search parallel --engine red --depth 5 --threads 4 --time-ms 5000 --progress
```

终端中约每 100ms 在 stderr 原地刷新，例如：

```text
search depth 5/10  [############--------] 60%  roots 24/40  elapsed 2.3s / 5.0s
```

百分比仅表示当前深度完成的根走法比例，每轮重新开始；每个走法耗时不同，
不代表整次搜索完成比例，也不估算剩余时间。用时在长分支搜索期间继续刷新。
并行搜索默认不限时；设置 `--time-ms` 后也显示时间预算。提前结束保留实际比例；
结束摘要中的 `selected depth` 表示最终采用的深度（0 表示未搜索的保底走法）。
时间限制允许完成已超过进度阈值的迭代，因此已用时间可能超过预算。
重定向 stderr 时只输出每轮结束及最终摘要，不输出终端控制字符。

库使用者可通过 `xq_engine_find_best_move_with_progress()` 或
`xq_engine_parallel_search_with_observer()` 传入可选 `XqSearchProgressFn`；
并行入口的末尾 `sampler` 参数传 `NULL` 时只报告进度，不采样。
两个并行入口均以 `const XqEngineAdapter *engine` 为首参，传入估值配置和真实对局历史。
事件仅覆盖根迭代开始、有效根走法完成和迭代结束，
在进入逐层加深前返回的根局面不产生事件；迭代结束不保证完成全部根走法。
并行根走法回调可能并发、乱序到达，应同步访问并合并同轮的最大完成数。
回调内不能修改或重入当前搜索；快照只在回调期间有效，全部回调在搜索返回前结束。
CLI 的显示线程和同步由独立模块负责，不改变递归搜索、缓存和剪枝规则。

## 走法路径采样

`--sample-search` 独立于 `--progress`，同时覆盖普通搜索和静态搜索：

```sh
./build/xiangqi_cli --search parallel --threads 16 --depth 10 --engine red \
  --progress --sample-search --sample-interval-ms 20 \
  --sample-output-dir build/search_samples
```

请求线程默认每 20ms 请求一次快照，每个搜索线程在检查点最多回复一次；
空闲、等待辅助任务的线程不计样本，旧快照不会被反复累计。
这是逻辑路径的协作采样分布，不是真实 CPU 占比、精确节点访问数或搜索主变。
辅助线程继承从根局面到任务拆分点的完整走法前缀。
仅开启原有 `--progress` 不维护采样路径，也不创建采样控制器。

TTY 中额外显示近期 5 秒的采样摘要；非 TTY 仍收集并写文件。
每次引擎思考在输出目录下创建独立目录，包含局面和配置、按迭代深度分组的
JSON 聚合报告及 `.folded` 折叠栈文件，可供火焰图工具使用。
目录时间戳使用 UTC；样本时间戳使用单调时钟，不是日历时间。
采样请求和报告处理使用独立线程。路径在回调返回前深拷贝，与状态事件、迭代边界
一起进入统一 FIFO；默认最多缓存 65,536 个事件，满时等待消费，不再覆盖样本或丢弃状态。
文件 I/O 在报告线程执行，不持有回调队列锁；退出时先停请求，再排空并发布剩余事件。
小报告的全量检查点至少间隔 5 秒；达到 524,288 节点后至少间隔 60 秒，
并按最近全量写入耗时的 10 倍自适应延长。每轮/搜索结束仍强制发布完整报告，
使用临时文件重命名保证对应字典和清单一起更新。
JSON 分开记录前缀累计样本与节点自身样本；折叠栈权重使用自身样本，避免重复计数。
路径最多保留 1024 步根前缀，并报告实际普通/静态层数及截断标记。
CLI 默认不设置每迭代统计内存的人工上限；可用 `--sample-statistics-max-mib N`
指定正整数 MiB 预算，`0` 表示不限额。统计节点按固定页增长，扩容只调整页目录，
不会搬移整棵节点树；`statistics_bytes` 记录已分配的统计空间。
显式预算耗尽、实际分配失败或节点 ID 范围耗尽时，仍报告未收录样本及不完整标记。
延迟、无效回调及资源失败仍明确记录；旧报告的槽覆盖计数保持兼容。
1 ms 是协作采样请求间隔，不保证空闲或尚未到检查点的线程每毫秒都有样本。
缓冲背压可延长搜索耗时，换取已产生的有效回调不因队列满而丢失；
记录仍受显式配置的预算及实际内存/磁盘可用量限制，失败不会伪装完整。
采样不修改搜索深度、重复局面、剪枝或时间限制策略，但会影响实际运行速度。

库调用可创建 `XqSearchSampler`，由观察线程调用 `xq_search_sampler_request()`，
通过串行 `xq_engine_find_best_move_with_sampling()` 或并行
`xq_engine_parallel_search_with_observer()` 入口借给搜索。
路径和线程状态经 `XqSearchProgressFn` 的新增事件传回；
样本及路径指针仍只在回调期间有效，使用者须在返回前复制。
控制器只能用于一次搜索，搜索和观察线程都退出后方可销毁。

回放忠实于搜索记录，不额外过滤可能尚未被搜索淘汰的伪合法走法。
文件是累计快照；搜索期间重新选择报告目录即可读取最新检查点。

大于 16 MiB 的迭代报告会分块读取、逐节点建立路径树，避免超过浏览器的单字符串容量限制；
读取时显示进度，切换报告或选择示例会取消旧加载。全部路径仍会保留，内存用量随节点数量增长。

原 `--sample-search`、`--progress` 的使用方式保持兼容。

## 固定视角并行搜索（macOS / Linux）

默认仍使用原引擎。通过 `--search parallel` 选择可读性优先的并行 Minimax：

```sh
./build/xiangqi_cli --search parallel --depth 5 --threads 4 --split-percent 50 --engine red --search-detail
./build/xiangqi_cli --search parallel --split-strategy interleaved --threads 4 --depth 5
```

并行模式默认迭代加深最大深度 **3**、总线程数 **2**（包括调用线程）、连续分块策略 **contiguous**、分配比例 **50%**。
`--depth` 必须为正整数；从深度 1 逐层搜索到该上限，默认不限时，也可用 `--time-ms` 设置预算。
遇到终局、找到必胜走法或时间停止时提前结束。所有轮次复用同一个线程池，
每轮等待辅助任务结束后才开始下一轮。超时中断时返回上一完整轮结果；若第 1 轮尚未完成，
使用该轮已完成的候选，没有完成候选时返回未搜索的合法保底走法。
缓存关闭且完整完成一轮时，评分对应该轮深度的精确求值；
缓存开启时与原引擎一致，允许复用更深搜索的结果，因此不保证与严格固定深度的无缓存分数相同。
`--split-strategy contiguous|interleaved` 选择拆分策略，仅用于 `--search parallel`。
每个普通搜索节点在完成所有着法排序后，只有剩余普通搜索深度至少为 **5 层**时，
才允许进行一次任务分割，将部分走法分配给空闲辅助线程。门槛由 `src/parallel_search.c` 中的
`PARALLEL_MIN_SPLIT_DEPTH = 5` 控制，修改后需重新编译。
一层指一方走一步，包含当前节点到子节点的这一步，不计静态搜索扩展。
不足 5 层的节点由当前线程完成搜索；剪枝、终局和超时仍可使任务提前结束。
默认最大深度为 3，因此默认配置不会派发辅助任务；搜索达到第 5 轮时才可能开始拆分。
两种拆分策略如下：

- `contiguous`：最多使用一个辅助线程，从着法列表尾部取 `ceil(孩子数量 × 比例 / 100)` 个，
  并至少留一个给当前线程。
  比例范围为 0..100，`--split-percent 0` 关闭拆分。
- `interleaved`：按排序后的走法顺序，在当前线程和辅助线程之间轮流分配。
  每个节点的参与线程总数上限由 `src/parallel_search.c` 中的
  `PARALLEL_INTERLEAVED_SPLIT_THREADS = 2` 控制，包含当前线程，修改后需重新编译。
  实际参与线程数为 `N` 时，当前线程搜索下标 `0、N、2N…`，第 `k` 个辅助线程搜索
  `k、k+N、k+2N…`（`k` 从 1 开始）。当前两线程时分别为 `0、2、4…`、`1、3、5…`。
  空闲线程不足时按实际数量缩减，参与数量也不超过走法数量；不等待线程腾空。
  常量设为 1 时关闭交错拆分，设为 2 时使用当前的奇偶划分，必须为正整数。
  完全忽略 `--split-percent`，包括 `0`；该参数仍须在 0..100 范围内。

全局线程数仍由 `--threads` 控制，默认值仍为 2。要让单个节点使用三线程交错划分，需先将
`PARALLEL_INTERLEAVED_SPLIT_THREADS` 改为至少 3 并重新编译，再设置 `--threads 3` 或更大值，
同时满足深度门槛、至少三个候选走法且有两个空闲辅助线程。
两种策略都可以用 `--threads 1` 进行串行对照。辅助线程内部仍可继续分裂，根节点和内部节点
使用相同策略和深度门槛。任务完成通知创建失败时，停止继续获取辅助线程，按已成功准备的数量分割；
没有成功准备的辅助任务或孩子少于两个时，当前线程搜索全部孩子。不创建积压队列，也不进行任务窃取。
即使发生剪枝或取消，节点也会等待全部辅助任务完成，再整理结果并释放任务记录。

并行搜索为每个工作线程设置至少 **32 MiB** 的栈；系统默认值更大时保留默认值。
大小由 `src/parallel_search.c` 的 `PARALLEL_MIN_WORKER_STACK_BYTES` 控制，修改后需重新编译。
`--threads 16` 包含调用线程，因此会创建 15 个搜索工作线程，合计至少预留 480 MiB
的栈地址空间，实际驻留内存随使用情况变化。调用线程的栈大小不受此设置影响。
增大栈可容纳更深的递归，但不能保证任意搜索深度都不会溢出。

实现位于 `src/parallel_search.c`，接口为 `include/xiangqi/parallel_search.h` 中的
`xq_engine_parallel_search`。库调用通过 `XqParallelOptions.split_strategy` 选择
`XQ_PARALLEL_SPLIT_CONTIGUOUS`（默认）或 `XQ_PARALLEL_SPLIT_INTERLEAVED`。
调用形式为 `xq_engine_parallel_search(&engine, &pos, &options, &result)`；
`xq_engine_parallel_search_with_observer()` 在相同参数后附加回调、回调用户指针和可选 `sampler`；
`sampler` 传 `NULL` 时关闭采样。旧签名中的独立 `evaluate`、`evaluate_user` 参数已移除，调用方需将其迁移到适配器。
`XqEngineAdapter` 中只使用 `static_evaluate`、`user`、`history`，
`score_move` 和串行 `transposition_table` 不参与并行搜索；并行表仍由 `options.transposition_table` 提供。
`engine` 为 NULL 时使用默认估值并关闭真实对局历史的根走法过滤；`static_evaluate` 为 NULL 时使用默认估值，
实际估值用户指针为 NULL。适配器及借用的历史、估值数据在搜索返回前保持有效，
调用方不能在搜索期间修改适配器、历史或估值参数。
普通搜索的评分区间和最终结果采用本次根方的视角：根方是 MAX，对方是 MIN。
根节点生成合法着法，内部节点使用伪合法着法并在下一层排除暴露己方将帅的分支；
首轮根节点及内部节点复用原引擎的基础着法评分，稳定降序排列：普通着法为 0，吃子着法为
`100000 + 被吃棋子价值 × 16 − 行棋棋子价值`，同分保持原顺序。MAX、MIN 节点都优先搜索
当前行棋方的高分着法。随后依次将匹配的缓存着法、上一轮 PV（主变化路线）着法移到最前，
最终优先级为 **PV > 缓存 > 基础排序**。终局和缓存直接返回的节点跳过基础排序；
深度零转入静态搜索，只使用静态搜索自身的基础吃子排序，不使用缓存或 PV 提示。
后续轮次按上一轮根节点孩子的评分上界稳定降序排列着法，并将已证实的最佳走法放在首位；
这些值仅用于排序，每轮重新建立评分区间，后续根节点不重复基础排序。
无缓存时也保留根节点排序和完整路径上的 PV 提示。
深度零叶子进入静态搜索（quiescence）：未被将军时以静态估值作为 stand pat，并继续搜索吃子；
被将军时禁止 stand pat，搜索全部合法应将，包括不吃子的走法。并行静态搜索统一生成伪合法走法，
在搜索循环中按是否被将军过滤：未被将军时跳过非吃子；被将军时试走，若原行棋方仍被将军，
则撤销并跳过该走法。每个深度零入口以入口局面初始化独立的栈上历史，只记录本次静态搜索
递归链，不包含真实对局历史或普通搜索路径，兄弟分支互不影响。静态搜索复用下述根走法的
三轮循环规则，过滤会使走子方判负的走法；生成列表原本为空，或被将军但没有剩余合法应将时，
判当前行棋方负。未被将军时保留 stand pat，不额外检查是否存在合法走法。
另外，仅在本次静态搜索链中，连续六步实际走子都将军（双方各三次）时，第六步后的局面若已被
将死仍判负，否则该分支以 0 分判和，优先于三轮循环判负。任何一步未将军都会中断连续计数，
入口局面原本被将军不计入。会完成第六次连续将军的合法着法即使符合循环判负规则也保留，
父节点仍可选择其他评分更高的走法。
将帅、将死、上述判和、循环过滤及无合法应将的检查优先于延伸上限。
静态搜索最多延伸 500 个半回合，到达上限时，未被将军则直接静态估值；被将军则在同一循环中
确认至少有一条未被循环过滤的合法应将，撤销试走后再对原局面静态估值，不继续递归。
在第 500 步达到连续六次将军时仍按上述优先级判断，但不会为满足判和条件延伸第 501 步。
此时无需对走法排序。
静态搜索在当前线程内执行，不再拆分任务；不同普通搜索分支的静态搜索仍可并发进行。
它使用行棋方视角的 negamax，递归窗口为 `[-beta, -alpha]`，孩子返回的分数取负。
估值回调直接接收当前行棋方视角，其结果截断后用于 negamax；同一局面的双方视角评分必须互为相反数。
普通搜索在调用静态搜索时转换窗口，返回后将分数转回根方视角，保留上下界语义及时间、祖先取消检查。
静态搜索不读写置换表、不扩展 PV；其历史在每个入口重新开始，不依赖调用方路径，
普通搜索节点仍可缓存包含静态搜索结果的评分。
普通搜索没有合法着法判负；静态搜索采用上述列表和应将判断。胜负分为 ±30000，普通估值截断至 ±28999。
自定义估值回调及其用户数据必须支持并发调用；输入棋盘不会被修改。

并行搜索与内置搜索共用真实对局历史的根走法循环过滤。`engine.history` 为 NULL、空历史，
或末条局面哈希与当前根局面不匹配时关闭过滤。当前规则会排除完成第三段连续相同周期的走法：
每段为正偶数步，三段走法的起终点序列逐步相同，四个边界局面的哈希一致，完成第三段的一方判负。
真实对局历史的根走法过滤只在迭代加深前执行一次；普通搜索不检测自身路径内的重复，
并行静态搜索另按上述规则检查自身递归链。搜索走法不会写入真实历史，内置搜索行为不变。
CLI 已为两种搜索传入同一份真实历史，自动走棋、指定电脑应手和悔棋均同步维护它。
根候选总数、进度和超时延长比例均基于过滤后的走法。全部候选被排除时，返回原合法保底走法，
`score_available` 为 false、`selected_move_depth` 为 0，不启动迭代或发送进度事件。

PV 参照原引擎最多保存 64 步，超出时只截断排序提示，不限制实际搜索深度。上一轮 PV 在本轮
保持只读，只有按起终点匹配提示首步的分支才继承后缀。所有排序在分配辅助任务之前完成。
当前线程与辅助线程各保存本批次最佳孩子的 PV，节点等待辅助任务完成后，按最终最佳孩子
拼接路线；不为每个候选着法保存完整 PV。取消结果不提供 PV，也不参与评分汇总。
PV 只用于排序，不作为评分或剪枝依据，不新增公开配置、排序回调或 PV 输出。

每个普通搜索节点单独保存已证实区间 `[lower, upper]`。MAX 对孩子的上下界分别取最大，MIN 分别取最小；
尚未搜索的孩子保留完整未知区间。严格 MAX 祖先的下界最大值提供 alpha，严格 MIN 祖先的
上界最小值提供 beta。运行中的分支在节点入口、领取着法、提交结果和辅助线程退出后沿父链
读取最新边界，因此其他线程更新祖先后，已经开始的深层普通搜索也能利用新门槛剪枝。
静态搜索将入口窗口快照转换为行棋方视角，再使用递归局部窗口，期间仍检查祖先停止状态；
返回分数转回根方视角后，按原入口窗口转换为精确值、上界或下界区间，不将剪枝分数当作精确值。
本节点值域与祖先窗口分开：剪枝返回已证实区间，取消不作为分数返回。
同分保留首先证实的最优着法。无缓存时，线程调度可能改变同分选择，但不改变根方分数；
启用缓存后，不同深度条目的命中及并发替换也可能影响评分。

并行模式使用独立的进程内置换表，CLI 默认创建并整局复用；创建失败则提示并继续无缓存搜索。
当前并行表与内置表均为 `2^24` 个四路桶（16,777,216 个桶），固定容量各为 `2^26`
（67,108,864）条目，分别由 `PARALLEL_TT_BUCKET_COUNT`／`PARALLEL_TT_BUCKET_SIZE` 和
`XQ_TT_BUCKET_COUNT`／`XQ_TT_BUCKET_SIZE` 控制。表结构和替换策略参照 `engine.c`：完整
64 位局面键、精确值/上下界、缓存深度和 8 位代龄，保留评分为 `8 × depth − 4 × age + 精确值奖励 3`。
局面键包含行棋方；与原引擎相同，不额外存棋盘校验 64 位哈希碰撞。
每轮迭代递增代龄，轮次间保留缓存条目，命中刷新代龄，深度零不入表。

缓存分数统一为行棋方视角；内部节点仅在缓存深度足够且为精确值或能直接剪枝时复用分数，
其余命中仅用于排序。根节点首轮只查询缓存着法，不直接返回缓存分数，后续轮次采用上一轮排序。
MIN 节点的分数、窗口和上下界会转换视角；缓存边界仍作为区间返回，不提升为精确值。
所有终局和非法走法检查保持优先，取消节点不入表，写回前必须等待辅助任务结束。
只要本次根候选因历史循环被过滤，根结果就不写入仅以局面为键的置换表；
后代结果仍可缓存，历史变化本身不清空表。

精确缓存命中直接返回时，沿深度足够的精确条目重建 PV；边界缓存不重建后续路线。
重建逐桶读取受保护的快照，在棋盘副本上匹配生成的着法并检查走法合法性；遇到终局、
条目缺失或竞争、深度不足、非精确条目、着法不匹配或非法、达到容量时停止并保留已有前缀。
因此 PV 可能短于搜索深度。重建命中会刷新条目代龄，但不计入缓存查询、命中或剪枝统计。

各桶使用一次 CAS 尝试独占访问，竞争时跳过该次查询或写入，不阻塞、不自旋。
这是桶级尝试占用，不是多字段无锁快照；普通条目字段均在占用期间读写，读者取副本后再释放桶。
每个物理搜索线程单独累计统计，线程结束后汇总，避免共享计数器竞争。

库调用默认关闭缓存。使用 `xq_parallel_transposition_table_create()` 创建表，赋给
`XqParallelOptions.transposition_table` 后可跨次复用，结束后用对应的 `destroy()` 销毁。
同前缀的 `clear()` 清空条目、代龄、评估绑定和统计；`reset_stats()` 只清统计；
`get_stats()` 返回 `XqTranspositionStats` 中的 probes/hits/cutoffs/stores/replacements。
桶竞争导致的查询跳过仍计入 probes，不算 hit；跳过的写入不算 store。
同一张表只允许一场顶层搜索及其辅助线程使用，外部查询统计、清空和销毁必须等搜索返回。
不同表可用于同时进行的独立搜索。Windows 创建返回 NULL，搜索仍返回不支持。

更换实际评估函数或用户指针时自动清空表；自定义评估更换根方时也保守地清空表。
内置评估支持跨根方复用。自定义评估须对同一局面和视角返回稳定结果；如果原用户指针指向的
评估参数发生变化，调用方必须主动清表。该表不与 `engine.c` 的置换表或磁盘格式混用。

并行模式支持 `--time-ms` 和走法后附加正整数毫秒数；单步覆盖后，下次省略时间恢复启动默认，
启动时未设置时间则恢复不限时。库调用通过 `XqParallelOptions.time_limit_ms` 设置预算，0 表示不限时。
预算使用单调墙钟，覆盖根候选准备、线程池创建及所有迭代。首次检测超时时，若当前未完成轮次
已完成的根候选比例严格超过 **15%**，允许完成该轮后退出，不再开始下一层；否则协作取消当前轮。
计时失败始终停止。返回前会等待所有辅助任务和回调结束，实际耗时可能超过预算。
并行模式仍不支持 `--tt-file` 和 `save-tt`。普通走棋、指定电脑应手、悔棋、翻转照常使用。
原模式默认深度 10 和限时行为保持不变。Windows 可以编译、使用原引擎，新模式返回不支持。

`--search-detail` 记录并行搜索的局面、状态、最佳走法、根分数可用性及类型、预算、
实际完成和选着深度、节点数、停止状态、耗时、线程数、拆分策略和分配比例。
`score_available` 为 false 时不使用 `score`；部分第 1 轮的分数为下界，其余有效结果以 `score_kind` 为准。
`split_strategy` 为 `contiguous` 或 `interleaved`；交替模式仍记录原始 `split_percent` 配置值，
并通过 `split_percent_note` 标明比例被忽略。帮助及启动信息也说明交替模式的比例不生效。
并行结果的 `stats` 提供每次调用的 `XqSearchStats`，其中进度总数为过滤后的根候选数。
节点数包含普通搜索和静态搜索函数的进入次数，普通叶子转入静态搜索时各计一次；
完成深度和选着深度只计算普通搜索层数，不包含静态搜索延伸。
不收集分裂次数、边界更新次数和取消次数；`--parallel-trace`、旧的逐节点跟踪回调及其公开类型已移除。
`--progress` 只观测根迭代进度。普通引擎的统计和详细日志保持原有行为。

节点的 `value.lower/upper`、`alpha/beta` 和 `state` 使用 C11 原子读写。
`state` 将原来的 finished/cancelled 合并为运行中、正常结束、取消三个状态，通过一次 CAS
发布终态，避免两个独立布尔值被并发更新后出现不一致。第一个发布成功的终态保持不变。
`check_node()` 无需任何锁即可刷新祖先窗口、判断剪枝、发布完成或取消，无需锁内复查；
alpha 通过 CAS 只增不减，beta 只减不增，较旧的扫描结果不能覆盖更强的边界。
读取旧边界最多造成额外搜索，不会错误剪枝。构建要求目标平台支持始终无锁的 `atomic_int`。

孩子结果提交和汇总也无需搜索锁：评分边界及 `submitted_bound` 用 CAS 更新，完成这些更新后才
通过 `submitted_count` 的 acq_rel 原子累加发布提交。最后一个提交者可见此前所有提交，才收紧
依赖全部孩子结果的另一侧边界。每个 `children[i]` 由一个线程写入一次；`best_index` 通过
release/acquire CAS 发布对应结果，避免索引与评分不一致，同分保留先成功发布的最佳索引。

线程池用原子 worker 状态及信号量调度，完成通知属于每次任务，由双方引用计数保护生命周期。
辅助线程完成后自行发布空闲状态，不必等待分配方领取结果。节点结束后仍须等待该任务的完成通知，
才能复制结果并释放节点。每个任务持有独立棋盘。它不保证比原引擎更快，
浅树上调度、缓存操作及额外分支搜索可能更慢。

## 原引擎的限时搜索与对局操作

启动时可用 `--time-ms` 设置整局默认的每步思考时间（正整数，单位毫秒），例如 2 秒：

```sh
./build/xiangqi_cli --time-ms 2000
./build/xiangqi_cli --engine red --time-ms 2000 --search-detail
```

不传此参数时使用引擎默认的 3000 毫秒。引擎先手时的第一步也使用该设置。

启动时可用 `--depth N` 设置整局最大搜索深度，默认 10 层，每层为一方走一步（ply）：

```sh
./build/xiangqi_cli --depth 12 --time-ms 5000 --search-detail
```

`N` 必须是 1 至 `INT_MAX` 的整数；缺少参数、零、负数、小数、溢出或多余非空白字符会被拒绝。
该设置也用于引擎先手的第一步，悔棋后继续保留；走法后附加时间不会改变深度上限。
搜索采用迭代加深，实际达到的深度受时间预算影响；获准超时延长也只完成当前层，不超过深度上限。

轮到玩家时，可以在走法后附加引擎下一步的思考时间（正整数，单位毫秒）：

```text
b2b9 2000
```

这表示走出 `b2b9` 后，引擎下一步最多思考约 2 秒；搜索也可能因达到深度限制等原因提前结束。
只输入走法（如 `b2b9`）则使用 `--time-ms` 指定的时间，未指定时为 3000 毫秒；深度限制使用 `--depth` 设置，默认为 10 层。
时间设置仅对紧接着的一次引擎搜索生效，下一次省略时间时恢复默认值。
时间为零、负数、小数、溢出或带有多余参数的输入会被拒绝，棋盘保持不变。
引擎先手时的第一步仍使用默认限制。整局复用同一张置换表，修改思考时间不会清空或重建它。

也可以在同一行指定玩家走法和电脑应手，例如玩家执红、电脑执黑时：

```text
a0a1 a9a8
```

第二步在第一步完成后的局面中验证，合法时直接代替本次电脑搜索；两步执行后重新轮到玩家。
电脑执红时同样适用：第一步是玩家的黑方走法，第二步是指定的红方应手。电脑先手的开局
第一步仍自动搜索，不新增输入提示。终端会用 `specified by player` 标明手动指定的电脑走法。

走法必须恰好是四字符坐标，列字母不区分大小写，输入项之间可用空格或制表符分隔。
只接受单走法、走法加正整数时间、双走法三种格式，不支持一行三步或双走法再附加时间。
任一步非法或格式错误，整行不执行，棋盘、历史和搜索限制保持不变；如果第一步已经结束
对局，请单独输入第一步，不要附带电脑应手。手动应手不改变默认深度、时间或电脑颜色。
两步都会记入真实走棋历史，后续搜索和悔棋照常使用；`undo` 一次撤回这两步。
开启 `--search-detail` 时，手动应手追加独立的 `--- manual engine move ---` 记录，包含
回合编号、电脑颜色、走法及电脑落子前后的 FEN，不产生搜索统计。

对局中输入 `undo`（或 `u`）可以悔棋：撤回玩家上一手以及引擎随后的一手，回到玩家走棋前。
可以连续输入以撤回多个回合；尚未走过玩家走法时会提示无法悔棋，引擎的开局首步不会单独撤回。
分出胜负后 CLI 保留输入提示，可以输入 `undo` 继续对局或 `quit` 退出；
如果玩家最后一手已获胜、引擎尚未回应，则只撤回玩家这一手。
悔棋会同步恢复棋盘和走棋历史，后续搜索仍复用原置换表。
上一手的临时时间限制不保留，重新走棋时可以再次指定；省略时仍使用启动时的默认时间。
开启 `--search-detail` 时，悔棋会追加 `--- undo ---` 记录（撤回步数和恢复后的 FEN），已有搜索记录保留。

输入 `flip` 可以将棋盘显示旋转 180 度，再次输入恢复原方向。
默认红方在下；反转后黑方在下，行号从上到下为 `0` 到 `9`，列标从左到右为 `i` 到 `a`。
反转仅影响显示，不修改棋盘存储、当前走棋方、走棋历史、FEN 或置换表。
走法仍按棋盘上标注的原始坐标输入，例如 `b2b9` 的含义不变。
显示方向会保持到再次输入 `flip`，走棋和悔棋不会重置它；对局结束后的输入提示中也可使用。

在玩家输入提示或对局结束后的提示处，输入 `save-tt PATH` 可以保存当前置换表：

```text
save-tt build/cache.tt
save-tt "build/my cache.tt"
```

路径必须指定；命令名后的全部内容作为路径，可以包含空格，也支持外层单引号或双引号。
交互输入不做 shell 变量、`~` 或转义展开；相对路径从当前工作目录解析。
整行最多 4095 字节，超长输入会完整丢弃，不会使用截断的文件名。
保存成功后替换已有文件，不自动创建父目录。写入采用同目录唯一临时文件，完整写入并成功关闭后再替换，
失败时保留旧文件并继续对局。保存不改变内存中的置换表、统计、棋盘和搜索时间。

下次启动时通过 `--tt-file PATH` 加载：

```sh
./build/xiangqi_cli --tt-file build/cache.tt --time-ms 5000
./build/xiangqi_cli --engine red --tt-file "build/my cache.tt"
```

加载在第一次搜索前完成，包括引擎先手的情况；之后继续复用和更新这张表。
文件不存在、损坏、版本不兼容或内存不足时会报错退出，不会悄悄改用空缓存。
不传 `--tt-file` 时沿用原行为。程序不会自动保存，也不提供运行时加载命令。
**保存的是搜索缓存，不是对局存档**：不保存或恢复棋盘、FEN、走棋历史、显示方向或时间设置。
初始局面仍由标准开局或 `--fen` 决定；加载后走棋、悔棋和翻转显示仍复用该表。

缓存使用小端二进制格式，包含格式版本、引擎缓存兼容版本、表尺寸、代数和有效条目，
并使用 IEEE CRC32 校验完整性。加载保留条目原槽位、深度、分数类型和代数，统计从零开始。
加载时也要求桶数量和每桶条目数与当前常量一致；此前以 `2^18` 个桶保存的文件无法载入当前
`2^24` 桶的内置表，即使文件和引擎缓存版本号相同，也会因表尺寸不匹配被拒绝，需重新搜索并保存。
空表也可以保存和加载；加载会先验证临时存储中的全部数据，失败不改变原内存表。
`engine.c` 中的 `XQ_TT_FORMAT_VERSION` 管理文件布局，`XQ_TT_ENGINE_VERSION` 管理搜索缓存语义。
修改评估、搜索分数语义、棋子编码或 Zobrist 哈希时必须升级引擎缓存版本，旧版本文件将被拒绝。
当前引擎缓存版本为 2，文件布局版本仍为 1。杀棋分已改为固定胜负分，版本 1 的旧缓存
会按不兼容文件拒绝加载，不能直接复用或自动迁移；请不加载旧缓存重新搜索，再保存新缓存。
版本检查不会自动识别未升级版本号的代码修改；该格式仅用于内置引擎，不应混用不同评估或搜索实现的缓存。

开启每次引擎走棋的搜索摘要：

```sh
./build/xiangqi_cli --search-detail
./build/xiangqi_cli --engine red --search-detail
./build/xiangqi_cli --search parallel --threads 4 --engine red --search-detail
```

默认不记录日志。开启后，向**当前工作目录**下的 `build/search_detail.txt` 追加文本；
缺少 `build` 目录时自动创建。每次启动写入时间、初始 FEN 和引擎执棋方，
每次引擎搜索结束后立即写入并刷新一份摘要。旧对局保留，人类走棋不会触发额外搜索。
文件创建或写入失败会输出警告并关闭本次运行的日志功能，对局继续。

每份摘要包含回合编号、走棋前 FEN、执棋方、搜索成功状态、最终走法，以及以下字段：

| 字段 | 含义 |
| --- | --- |
| `depth_limit` / `time_limit_ms` / `time_mode` | 本次搜索配置，默认 10 层、3000 毫秒、单调墙钟；可通过 `--depth` 设置最大深度、`--time-ms` 设置默认时间，输入走法时可指定下一步的时间限制 |
| `max_started_depth` | 实际开始搜索至少一个根走法的最大迭代深度 |
| `iteration_progress` | `max_started_depth` 所属轮次已完成的根候选数量／过滤后的候选总数及百分比，例如 `12/44 (27.3%)`；从未开始搜索时为 `not-started (0/N)` |
| `completed_depth` | 全部根候选走法均已完成的最大迭代深度 |
| `selected_move_depth` | 最终选棋依据所属的搜索深度；超时回退时对应上一完整轮，未经搜索的兜底走法为 0 |
| `nodes` | 普通搜索和静态搜索函数的进入次数，普通搜索叶节点转入静态搜索时各计一次 |
| `elapsed_ms` | 整次调用的单调墙钟耗时，读取失败显示 `unavailable` |
| `stopped` | 是否检测到时间限制或搜索计时错误；获准延长并完成当前轮时也为 `yes` |
| `winning_move_found` | 是否因某个根候选正常返回正向杀棋分数而立即选用该走法并结束搜索 |
| `stats_available` / `cache_available` | 内部搜索统计／置换表统计是否可用 |
| `cache_probes` / `cache_hits` / `cache_hit_rate` | 本次置换表查询数、命中数和命中率；查询为零时为 `0.00%` |
| `cache_cutoffs` | 缓存分数直接复用或上下界导致剪枝的次数 |
| `cache_stores` / `cache_replacements` | 本次缓存写入和替换次数 |

并行模式同样输出上述 `cache_*` 字段，计数为本次搜索各线程的汇总，而非置换表跨次搜索的累计值。

搜索进度在每步搜索结束后写入摘要，按根候选数量计算，不代表耗时或搜索节点的完成比例。
中途被打断的候选不计入完成数；完整轮次显示 `N/N (100.0%)`。超时回退到上一完整轮选棋时，
进度仍保留最深已开始轮次的实际完成情况；若下一轮尚未开始就超时，则保留上一轮的完整进度。
没有合法候选或候选全部被历史循环过滤时显示 `not-started (0/0)`，不计算百分比。

三个实际深度均以半回合（ply）为单位，不包含静态搜索延伸；未开始搜索时为 0。
搜索发现第一个正常完成且分数为 `XQ_WIN_SCORE`（固定为 +30000）的根候选时，
立即选用该走法，不再搜索其余候选或继续加深，也不回退上一轮；这沿用当前引擎的杀棋
评分定义，不保证选中最快取胜的走法。普通优势、负向杀棋分数和中断候选不触发此行为。
必胜统一为 `+30000`、必败统一为 `-30000`，不再表达杀棋距离，也不区分更快取胜或更晚失败。
内置搜索将普通静态评价（包括自定义评估回调的结果）限制在 `[-29999, 29999]`（`XQ_MAX_STATIC_SCORE`），防止静态
高分冒充已证明的胜负；直接调用公开静态评估函数时不作此限制。
内部 `negamax` 节点一旦通过已完成候选证明达到 `+30000`，就提交 EXACT 分数及最佳走法
到置换表并立即返回，写入仍遵循原有替换策略。仅返回同值上界不足以证明胜利，不提升为 EXACT。
静态搜索也在证明最高分后提前返回，但继续不写入置换表；普通及静态搜索的解释入口采用相同规则。
内部发现必胜只结束该节点，父节点仍取负并继续判断；日志的 `winning_move_found` 只表示根节点最终选到必胜走法。
此时 `winning_move_found: yes`，进度可能不足 100%，`selected_move_depth` 可能高于
`completed_depth`；后者仍只统计所有根候选完成的轮次。未搜索候选不使用旧轮评分，
未完成整轮的结果不作为根节点 EXACT 缓存写入，已完成的内部节点缓存保留。
找到必胜走法本身不设置 `stopped`；若在超时延长期间找到，两项都可以为 `yes`。

首次检测到时间限制时，若当前轮已完成根候选比例**严格超过 50%**，允许超出原时间预算，
继续完成当前轮并采用其结果（若提前找到必胜走法则立即返回），然后退出，不再进入下一层。例如 `21/42` 停止，`22/42` 继续；
恰好 `50%` 仍停止。阈值由 `src/engine.c` 中的 `XQ_FINISH_ITERATION_THRESHOLD_PERCENT` 常量控制。
剩余候选的耗时不均，额外用时不设上限；延长后 `elapsed_ms` 可超过预算，`stopped` 为 `yes`，
成功完成时进度为 `100.0%`，完成深度和所选走法深度均对应该轮。计时失败始终立即停止。
未获准延长或延长期间计时失败导致本轮中断时，选棋使用上一完整轮结果；仅在第 1 轮尚未
完成时使用该轮已完成候选，此时所选走法深度为 1、完整完成深度为 0。
缓存统计取本次调用前后的计数差，不清空缓存和累计计数。命中包含仅用于走法排序的命中，
不等同于可以直接复用缓存分数；无缓存时计数为零并标记 `cache_available: no`。

库调用方可通过 `xq_engine_find_best_move_with_progress()` 的 `stats` 参数获取相同统计；
不需要进度回调时，将 `progress` 和 `progress_user` 都传为 `NULL`。`stats` 也可以为 `NULL`；
只需最佳走法时，可使用 `xq_engine_find_best_move()`。
普通找最佳走法接口统一使用内置搜索，可获取其内部深度、节点和可用缓存的统计。

示例入口默认是“你执红，内置简易引擎执黑”。输入格式是 `起点+终点`，文件用 `a..i`，行号用 `0..9`，例如：

```text
b2b9
```

可用命令：

```text
moves  打印当前所有合法着法
fen    打印当前 FEN
help   打印帮助
quit   退出
```

## 搜索路径解释

`xiangqi_explain` 默认从初始局面搜索 4 层并进入交互浏览，支持 `--fen FEN`
和 `--depth N`。设置 `--time-ms`、`--moves` 或 `--tt-file` 后，只输出一次目标节点的信息并退出：

```sh
# 从根局面迭代加深，总搜索预算为 2 秒；默认最大深度与 CLI 相同，为 10。
./build/xiangqi_explain --time-ms 2000

# 载入置换表，单次解释根节点；也可组合时间预算和目标路径。
./build/xiangqi_explain --tt-file build/cache.tt
./build/xiangqi_explain --tt-file build/cache.tt --time-ms 2000 --moves a3a4 a6a5

# 从初始局面迭代加深至最多 4 层，查看路径 a3a4 a6a5；默认预算 3 秒。
./build/xiangqi_explain --depth 4 --moves a3a4 a6a5

# 也支持带引号的走法序列、参数换序和自定义根局面。
./build/xiangqi_explain --moves "e0d0 e5e4" --depth 4 --time-ms 2000 \
  --fen "4k4/9/9/9/4p4/9/9/9/9/4K4 r - -"
```

`--moves` 指定从根开始的完整搜索路径；程序在副本上检查每步是否合法，再从原始
根局面搜索。路径长度会消耗根搜索的深度：根深度为 4、路径长度为 2 时，目标节点
剩余普通深度为 2。只记录剩余普通深度至少为 1 的目标节点；到达深度 0 或进入
静态搜索的路径不生成解释记录。迭代加深时，从根深度大于路径长度的轮次起才可能记录目标。
重复的 `--moves` 按出现顺序追加；每段序列读取到下一个 `--` 选项。

单次模式的搜索规则与 CLI 一致，默认最大深度 **10**、时间预算 **3000 毫秒**。
`--time-ms` 必须为正整数毫秒，指定整个根搜索的单调墙钟预算；
路径校验、加载缓存和结果输出不计入预算。所有搜索都从 1 层迭代加深，同时设置
`--depth` 与 `--time-ms` 时，以先到的限制为准，但到时限时进度严格超过 50% 可完成当前层后退出。
库调用可设置 `time_limit_ms=0` 来禁用
截止时间，仍逐层迭代到 `max_depth`。单次模式拒绝 `--depth 0`；原有交互模式默认 4 层，
仍支持 `--depth 0` 和静态搜索浏览。

解释搜索不再采用独立的根缓存返回、根排序或额外计时规则。根驱动在每个根着法搜索
前后检查时间，普通递归与静态搜索沿用每 1024 节点检查；解释记录不增加时钟检查。
相同根局面、限制、历史、回调和初始置换表会使用相同的搜索规则，但记录信息本身有开销，
两次独立的墙钟限时运行仍可能在不同节点停止，因此不保证每次 6 秒搜索的落子完全相同。

`root_selection` 是本次根搜索最终选中的着法，与 CLI 的选棋策略一致。
找到正向杀棋分数的根候选后立即选用；此时选棋表保留发现该走法的本轮快照，未搜索候选显示 `-`。
完整迭代结束时按根分数选择；到时限时满足上述阈值则完成当前轮并采用其结果。若当前轮
因超时或计时失败被中断，则返回上一完整轮的最佳着法，候选表也恢复
为该完整轮的快照，不混用不同深度的评分。若第 1 轮尚未完成，选择该轮已完成候选中的
最佳着法；没有任何候选完成时使用与 CLI 相同的初始兜底着法。同分保留搜索顺序中最先
达到该分数的着法。若最后一个候选完成后才检测到超时，仍采用刚完成的整轮结果。

`policy` 优先显示 `winning-move`（发现必胜走法立即返回）；其他情况为 `completed-iteration`
（完整轮结果）、`timeout-completed-iteration`（较深轮中断后回退）、`partial-first-iteration`
（首轮部分结果）或 `fallback`（未经搜索的兜底）。
超时或发现必胜走法时的选棋表包含 `score`、`completed_depth` 和 `selected`，展示实际用于最终选择的快照。
分数是递归返回值，可能是边界；有效分数属于同一轮，未完成候选显示 `-`，不把占位值
当作有效分数。`selected_move_depth` 对应该快照中选中着法的深度。

输出的 `root_depth` 是目标记录所属的根迭代深度，`remaining_depth` 是目标节点剩余
普通深度；`alpha`、`beta` 和候选表来自实际根搜索，分数以目标节点行棋方为视角。
候选表的编号相对于目标节点；`best` 是该次访问的最佳候选行号，**不是最终根选棋结果**。
超时或发现必胜走法提前返回时，保留的完整目标记录与最终选择可能使用不同轮次的数据。
发现必胜走法时若根候选尚未全部搜索，不把这次根目标访问标记为完整；目标访问与最终选棋仍独立记录。
`exact`、`upper`、`lower` 分别表示精确值、上界和下界。
`complete=yes` 包含正常剪枝或直接复用缓存完成的节点，并不意味着遍历了其所有候选。

程序保留目标节点最近一次**已完成**的搜索记录，即使所属的根迭代尚未完成。
`completed_root_depth` 和 `stopped` 描述整个根搜索；它们可能与目标记录的轮次不同。
若目标从未完成，则展示最近一次访问的部分记录（`complete=no`、`partial_score`）；
被中断候选的占位返回值不会进入表格。若路径因剪枝、深度或超时而未被访问，输出
`path not visited with remaining depth >= 1 in this search`，正常退出且不额外搜索该局面。

库接口 `xq_engine_explain_path()` 使用独立的 `builtin_search_for_explain()` 根驱动，
按 `builtin_search()` 的规则执行搜索，复用相同的排序、计时、置换表及超时选棋辅助函数。
它接受适配器提供的评估、排序、置换表和历史信息。解释状态和
记录逻辑集中在独立上下文、`builtin_search_for_explain()`、`negamax_for_explain()` 中；
普通 `builtin_search()`、`negamax()`、`quiescence()` 和 `SearchContext` 不依赖解释记录。
两条命令从同一 FEN 启动时没有过去对局的历史；如要重现进行中的 CLI 对局，
库调用方还需提供相同历史。原有逐层解释接口和交互导航保持兼容。

`--tt-file PATH` 使用与 CLI 相同的缓存格式和兼容性检查；加载失败报错退出，不回退。
没有指定文件时，与 CLI 一样创建一张空置换表。搜索正常更新内存中的条目、代次及替换
信息，输入文件不会被改写。

根节点只在迭代前查询一次缓存着法用于排序，**不会直接复用根缓存分数**。
后续根迭代按上一轮分数排序，不再查询根缓存。`root_ordering_tt` 保留首次排序查询；
根目标记录在第一轮后的 `target_tt=not-probed` 表示该轮没有重新查询，而不是没有启用缓存。
内部目标节点仍允许按深度和分数边界直接返回，显示
`returned directly from transposition table; no candidates expanded`，缓存着法在 `target_tt`
中单独展示，此时 `best=0` 表示没有候选行。终局根节点在开始迭代前返回，`root_depth=0`，
没有最终着法。

新增缓存状态如下。它们描述节点入口处的实际查询，不是搜索结束后重新查询的结果。

| 状态 | 含义 |
| --- | --- |
| `disabled` | 没有提供置换表 |
| `not-probed` | 未查询，例如深度为 0、查询前判定终局，或第二轮及之后的根节点 |
| `miss` | 查询没有匹配条目 |
| `hit` | 找到条目但未直接返回；可能是深度/窗口不允许截断，或根节点只查询排序着法 |
| `direct` | 此节点的返回分数直接来自缓存 |

`target_tt` 显示目标节点的查询；候选表的 `child_tt`、`tt_depth`、`tt_score`、`tt_kind`、
`tt_best`、`hash_used` 显示直接子节点的查询。`tt_score` 和 `tt_kind` 以**子节点行棋方**
为视角，原有 `score` 和 `kind` 以**目标节点行棋方**为视角。缓存中的胜负分固定为 ±30000，
不包含将死距离，也不随查询节点的 ply 调整。`hash_used=yes` 表示缓存着法通过候选匹配并用于排序，之后 PV 提示仍可能
优先；它不表示直接返回。`reason=ordering-only` 表示根节点仅查询排序提示，
不根据缓存深度或分数决定返回。子树深处命中缓存不会把直接子节点标成 `direct`。

若严格祖先通过缓存直接返回，会显示 `latest_ancestor_cache_block`、祖先路径、当时的
窗口和剩余深度，以及 `ancestor_tt` 条目信息。这条事件与保留的目标记录各自标明
`root_depth`：它只说明那一轮在该祖先停止展开，不代表每一轮或最后一轮都因此未访问目标。
目标本身直接命中缓存算作已访问，不算祖先阻断。没有实际观察到缓存阻断时，不会把
未访问原因推断为缓存。程序不会为了补出解释而绕过缓存或沿缓存 PV 伪造访问记录。

`cache probes/hits/cutoffs/stores/replacements` 是本次调用的累计计数增量，不清零表中
原有统计。条目可能来自输入文件，也可能来自本次搜索的较早分支或迭代；这里不区分来源。

## 随机局面生成与批量搜索

构建后可以先生成一组可复现的随机合法局面，再让内置引擎逐个搜索：

```sh
./build/xiangqi_generate_positions
./build/xiangqi_search_positions
```

两个程序默认使用 `stats/random_fen/random_positions.fen`，也可以为二者指定相同的文件路径：

```sh
./build/xiangqi_generate_positions build/profile_positions.fen
./build/xiangqi_search_positions build/profile_positions.fen
```

生成器使用固定随机种子，从初始局面随机行走 `0..100` 步，共输出 100 个局面，每行一个 FEN。
搜索程序顺序读取一次文件，以最大深度 6、不限时的配置为每个局面搜索一步，适合作为性能分析的非交互式入口。

## AI 接入

外部 AI 可以直接复用规则层：

```c
XqMoveList legal;
xq_generate_legal(&pos, &legal);

for (int i = 0; i < legal.count; ++i) {
    XqPosition next = pos;
    xq_position_make_move(&next, legal.moves[i]);
    /* 在 next 上做搜索或评估 */
}
```

普通找最佳走法接口统一使用内置搜索；可以通过 `XqEngineAdapter` 接入自定义估值和
走法排序回调。以下示例在默认估值基础上，额外提高己方兵卒的价值：

```c
static int my_evaluate(const XqPosition *pos, XqColor perspective, void *user) {
    int pawn_bonus = *(const int *)user;
    int pawn_balance = xq_position_piece_count(pos, perspective, XQ_PAWN) -
                       xq_position_piece_count(pos, xq_color_opponent(perspective), XQ_PAWN);
    return xq_engine_default_static_evaluate(pos, perspective, NULL) + pawn_bonus * pawn_balance;
}

int pawn_bonus = 20;
XqEngineAdapter engine = {
    .static_evaluate = my_evaluate,
    .user = &pawn_bonus,
    .score_move = NULL,
};

XqMove best;
XqSearchLimits limits = xq_search_limits_default();
xq_engine_find_best_move(&engine, &pos, &limits, &best);
```

估值分数以 `perspective` 一方为视角，分数越高表示越有利；`user` 原样传给回调。
`score_move` 可设置为走法排序评分回调，为 `NULL` 时使用默认排序评分。
若需实现完整的外部搜索，应直接复用上述规则层接口。

## 坐标约定

- `file` 范围是 `0..8`，`rank` 范围是 `0..9`。
- 红方底线是 `rank = 0`，黑方底线是 `rank = 9`。
- `xq_square_make(file, rank)` 将坐标映射为 `rank * 9 + file`。
- FEN 按黑方到红方的 10 行书写，使用大写表示红方，小写表示黑方。
